Empirical study · Debian archive · September 2026

The Resilience Budget

A resilient module boundary buys recompilation-free evolution at a runtime cost. This measures which kinds of change actually happen across 946 consecutive releases of 152 C and C++ libraries — and therefore which resilience mechanisms earn that cost, and which are budget spent on events that almost never occur.

946 consecutive-release transitions 152 libraries 2,385 shared objects 818 C / 126 C++ transitions libabigail 2.6.0, amd64, DWARF from -dbgsym
The answer

What to build, and what to skip

Opaque struct layout Field added, removed, retyped, or shifted; type size changed. Load-bearing for 45 of the 84 releases a resilient boundary would fully rescue, and the sole reason for 34 of them.
Worth it
Non-frozen enums An added enum case moves no byte, so it is not a binary break — but it breaks any client that switched exhaustively. Load-bearing for 47 of 84 rescues, sole reason for 37. The single most common absorbable change kind.
Worth it
No implicit cross-module inlining Inline, in-class and template bodies changed in 23.2% of releases — more often than every struct-layout change combined. C and C++ have no defence, and no ABI tool can even detect it.
Worth it
Resilient vtable dispatch Vtables changed in 8 of 946 transitions (0.8%; 5.6% among C++ only) and were load-bearing for just 3 rescues. Real, but the thinnest return on runtime budget of the four.
Marginal
Removed symbols & changed signatures Present in 130 of 177 breaking transitions (73.4%). No indirection helps: a call that no longer type-checks is an API break, not an ABI one. This is the ceiling on what any resilience mechanism can deliver.

In C, vtable changes are essentially absent (1 of 818 transitions) and layout churn dominates. In C++, base-class changes are the single most common absorbable kind — 18.3% of transitions, 329 events — because a changed base rewrites both the subobject layout and the vtable of every derived class.

The blind spot

The most frequent hazard is the one no tool measures

Inline, in-class and template bodies

abidiff compares DWARF types and ELF symbols. abi-compliance-checker compares declared interfaces. A change to the body of a header inline function, an in-class method, or a template produces no output and exit code 0 from either — even with --harmless. It is invisible by construction, not merely rare. Yet C++ copies exactly those bodies into every client that included the header.

At 23.2%, inline-body churn is roughly six times more frequent than struct-field additions (4.1%) and twenty-nine times more frequent than vtable changes (0.8%). Worst single releases: OpenEXR 3.1.13 → 3.4.6 changed 95 of 173 shared bodies; isl 0.24 → 0.25 changed 66; xxHash 0.7.3 → 0.7.4 changed 31 of just 53. This is the strongest argument in the data for making cross-module inlining opt-in rather than automatic.

The SONAME mechanism is the only ABI-compatibility signal the C/C++ platform offers, and in this corpus it is used for roughly one break in fifteen. That is the background condition a resilient boundary is competing against — not a careful versioning discipline, but an unenforced convention.

Least stable in the corpus, by breaking transitions: hunspell 8/8, libde265 7/9, chromaprint 7/9, rubberband 7/9, snappy 7/8, srt 7/8, intel-gmmlib 6/9, sane-backends 6/7.

The verdict

Would a resilient boundary have saved the release?

Why the two rows differ, and why it matters

Adding an enum case moves no byte, so abidiff — correctly, for its purpose — does not call it an ABI break. Score only binary breakage and the enum mechanism is credited with zero by construction, even though added enum cases are the most common absorbable change in the corpus. Under the framing that matches what resilience is for, opaque layout and non-frozen enums come out roughly equal, and together account for essentially every rescue.

The ceiling is the real finding: even under the generous framing, 60.7% of affected releases contain a removed symbol or a changed signature. Resilience buys evolution headroom, not immunity — it converts a class of breaks that is common and mechanical into a non-event, while leaving untouched the class that arises from deliberate API redesign.

Method

Six ways this measurement goes wrong

Each was found by inspecting real tool output against a 30-case ground-truth suite — synthetic libraries with exactly one known change each, including four negative controls. Both analysers score 30/30. Skipping any one of these silently corrupts a whole change category.

01

Default abidiff hides enum-case additions. An added enumerator is filtered as harmless: the tool prints "0 Changed (1 filtered out)" and exits 0. --harmless is required. Without it, this study would have reported zero enum additions instead of 66.

02

--leaf-changes-only drops base-class insertions. Leaf mode is otherwise necessary — it reports each changed type once rather than once per referencing function — so both reports are parsed and merged.

03

Third-party types are attributed to the library. A public API drags in glibc's _IO_FILE and libstdc++'s std::tuple; when the build toolchain moves, that churn looks like the library changing its own layout. 1,213 events — including 477 phantom struct-field additions — were excluded by attributing each changed type to its declaring header.

04

--drop-private-types does not cover functions. dbus exports 657 _dbus_* internals under a version-stamped LIBDBUS_PRIVATE_* ELF node against 240 public symbols, so a routine release reads as "651 public functions removed". The flag drops private types only; symbols in a private version node must be filtered separately.

05

abipkgdiff cannot compare across a SONAME rename. It pairs ELF files by filename, so for ICU 72 → 73 it reports six "Removed binaries" and six "Added binaries", exit code 0, and performs no ABI comparison at all — silently skipping exactly the transitions where declared breaks live. Shared objects are paired by stem and compared with abidiff instead.

06

Some libraries rename every symbol by policy. ICU suffixes each symbol with its version (foo_72 → foo_73), turning one release into ~5,600 removals and ~5,600 additions. That is a naming convention, not 11,200 independent decisions; such transitions are detected and excluded rather than left to dominate the totals.

Scope

What this does and does not establish

Selection is automatic, not curated. Libraries are the most-installed lib* packages by Debian popcon that ship both a -dbgsym and a -dev package. C and C++ are quota'd separately because popcon's top ranks are almost entirely C system libraries — an unquota'd corpus yielded 743 C transitions against 22 C++.

"Consecutive releases" means consecutive upstream versions as packaged by Debian, deduplicated so that Debian-revision-only rebuilds are not counted as library evolution.

Reachability is not usage. A struct counted as publicly layout-visible is one reachable from the public API. Whether clients actually allocate or embed it — rather than only holding a pointer — is not measured, so layout-change counts are an upper bound on real client breakage.

The C++ sample is smaller. 126 transitions across 25 libraries; vtable changes rest on 7 of those. The direction (dispatch churn is rare relative to layout churn) is clear, but the exact rate is not tightly estimated.

The private-symbol filter removed 0 events in the sampled transitions — the dbus releases that motivated it fall outside the ten most recent. It is retained because the failure mode it prevents is severe.

Corpus built from snapshot.debian.org; ABI comparison with libabigail 2.6.0 (--leaf-changes-only --harmless, DWARF from -dbgsym, public API restricted via --headers-dir). Header-body analysis is a linear lexical scanner validated against the same ground-truth suite.
